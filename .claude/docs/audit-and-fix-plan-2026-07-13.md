## 0) كيف قرأت المشروع (منهجية الدراسة)

فحصتُ:
- **الباك-إند:** كل الطبقات (`Domain` / `Documents` / `Infrastructure` / `Api`)، مع تركيز على `AppDbContext`، الخدمات (`Auth`, `User`, `Delegation`, `Outgoing`, `Attachment`)، الـ Controllers، الـ Middleware، الإعدادات (`Program.cs`, `appsettings.json`, `DependencyInjection.cs`)، والـ Migrations.
- **الواجهة:** `models.dart`, `session.dart`, `api_client.dart`، وشاشات المستخدمين/الشركات المعدّلة.
- **القواعد:** `.claude/rules/*` (coding-standards, architecture, security, workflow).
- **الوثائق:** `progress-log`, `roadmap`, `status-report`, `decisions (ADR)`.
- **الـ git diff الكامل** للتعديلات غير المُودَعة، والملفات الجديدة/الغريبة.

**ما الذي تغيّر مؤخراً (جوهر التعديلات):** الانتقال من نموذج «شركة واحدة لكل مستخدم» (`User.CompanyId`) إلى نموذج **متعدد‑لمتعدد** عبر كيان `UserCompany` (`AssignedCompanies`). صاحَبَ ذلك:
- إضافة claim جديد في التوكن `cids` (قائمة معرّفات الشركات) بدل `cid` المفرد.
- تعديل `ICurrentUser` بإضافة `AllowedCompanyIds` وتغيير منطق `ActiveCompanyId`.
- **إزالة الـ Global Query Filter عن كيان `User`** والاعتماد على فلترة يدوية في `UserService`.
- إضافة **نقطة حذف جذري للشركة** (`DELETE /companies/{id}`) + زر بالواجهة.
- إزالة بذر الشركة الافتراضية من `DbSeeder`.

> ⚠️ هذا التعديل يخالف **ADR-006** (الذي ينصّ على `CompanyId` + Global Query Filter) دون إضافة ADR جديد، ويخالف مبدأ الأمان «لا تتجاوز العزل الصفّي» و«الحذف ناعم دائماً»، ويخالف **ADR-008** (تغليف المعاملات بـ ExecutionStrategy).

## 2) تفصيل كل بند (السبب الجذري + الإصلاح المقترح)

### 🔴 B1 — حذف الشركة يعطُب وقت التشغيل
**الموقع:** `CompaniesController.cs:134`
```csharp
using var tx = await db.Database.BeginTransactionAsync(ct);   // ← بلا ExecutionStrategy
```
**السبب:** `EnableRetryOnFailure()` مُفعّل في `DependencyInjection.cs:24`. تحت استراتيجية إعادة المحاولة، أي معاملة يدوية يجب أن تُغلَّف بـ `CreateExecutionStrategy().ExecuteAsync(...)` (هذا نصّ **ADR-008** والقاعدة في `coding-standards.md`). أول استعلام/حفظ داخل المعاملة يرمي:
`InvalidOperationException: The configured execution strategy 'SqlServerRetryingExecutionStrategy' does not support user-initiated transactions.`
**النتيجة:** نقطة الحذف تفشل بـ 500 دائماً (لهذا لم تعمل أصلاً — راجع `test_bug.dart`).
**الإصلاح:** غلّف المنطق كاملاً داخل `strategy.ExecuteAsync(...)` كما في `OutgoingService.ApproveAsync:141`. (لكن أولاً احسم قرار B2 — هل نحذف جذرياً أساساً؟)

### 🔴 B2 — الحذف الجذري يمحو وثائق رسمية
**الموقع:** `CompaniesController.cs:142‑143`
```csharp
db.OutgoingBooks.RemoveRange(... WHERE CompanyId == id);   // حذف فعلي للكتب المعتمدة
db.ArchiveDocs.RemoveRange(... WHERE CompanyId == id);     // حذف فعلي للأرشيف
```
**السبب:** يخالف مباشرةً قاعدة `security.md`: «الحذف ناعم دائماً (`IsDeleted`) — لا حذف فعلي». الكتب الصادرة **موقّعة رقمياً (QR/ECDSA) ولها أرقام رسمية**؛ محوها الفعلي يدمّر سجلاً قانونياً ويكسر أي تحقّق لاحق.
**الإصلاح المقترح (يحتاج قرارك — راجع D1):**
- **الخيار الموصى به:** استبدال الحذف بـ **تعطيل الشركة** (`IsActive = false`) — تختفي من الاستخدام دون فقدان بيانات.
- إن كان لا بد من حذف: **امنعه** إذا كان للشركة أي كتاب `Final` أو أرشيف (أعِد 409 برسالة واضحة)، واسمح بالحذف فقط لشركة «فارغة» أُنشئت بالخطأ، وبحذف ناعم على مستوى الشركة (`Company.IsDeleted`) بدل `RemoveRange`.

### 🔴 B3 — `reset-db` خطر إنتاجي
**الموقع:** `SystemController.cs:15‑19` — `EnsureDeletedAsync()` يُسقِط قاعدة البيانات ثم يُعيد البذر. محمي بـ `[Authorize(Roles="SuperAdmin")]` فقط، **بلا قيد بيئة**.
**الإصلاح:** قصْره على `IWebHostEnvironment.IsDevelopment()` (أعِد 404/403 خارج التطوير)، أو احذف النقطة من بناء الإنتاج، أو اطلب تأكيداً ثانوياً (كلمة مرور + عبارة تأكيد). لا يجوز إبقاء «مسح كل شيء» متاحاً بضغطة في الإنتاج.

### 🟠 B4 — عزل المستخدمين أصبح هشّاً و«يفشل مفتوحاً»
**الموقع:** `AppDbContext.cs:75` (حُذف `HasQueryFilter` عن `User`) + الفلاتر اليدوية في `UserService`.
**السبب:** الحماية الآن تعتمد على شروط يدوية مثل:
```csharp
if (current.ActiveCompanyId.HasValue && !current.IsSuperAdmin) { /* فلترة */ }   // ListAsync:30
if (current.ActiveCompanyId.HasValue) { /* تحقّق الانتماء */ }                   // Update:79 / Reset:117
```
عندما يكون المستخدم **غير سوبر أدمن وبلا شركة نشطة** (`ActiveCompanyId == null`، ممكن لأن النظام صار يسمح بمستخدمين بلا شركات) تُتخطّى الشروط → يصبح **بإمكانه سرد/تعديل/إعادة تعيين كلمة مرور لمستخدمين في أي شركة** (ضمن حدود الدور فقط). هذا «fail‑open».
**الإصلاح المقترح:** استعادة العزل التلقائي عبر Query Filter يشمل الإسنادات المتعددة، بدل الفلترة اليدوية المتناثرة:
```csharp
b.Entity<User>().HasQueryFilter(x =>
    !_filterByCompany
    || x.CompanyId == _companyId
    || x.AssignedCompanies.Any(c => c.CompanyId == _companyId));
```
وإبقاء `IgnoreQueryFilters()` فقط في المسارات المقصودة (تسجيل الدخول، فحص تفرّد الاسم، السوبر أدمن). بديلاً (أو إضافةً): اجعل الفلاتر اليدوية **تفشل مغلقة** — أي إذا كان غير سوبر أدمن وبلا شركة نشطة، لا يرى/يعدّل شيئاً.

### 🟠 B5 — تحديث المستخدم يمحو شركاته
**الموقع:** `UserService.cs:89‑103` مع `ResolveCompanies:142`.
**السبب:** عند التحديث تُمسح كل الإسنادات وتُعاد بناءً على `ResolveCompanies`:
```csharp
user.AssignedCompanies.Clear();
foreach (var cid in companyIds) user.AssignedCompanies.Add(new UserCompany { CompanyId = cid });
```
وبالنسبة لغير السوبر أدمن، `ResolveCompanies` تُرجع **شركته النشطة فقط** `[currentCid]`. فلو أسند سوبر أدمن مستخدماً للشركات [1،2،3]، ثم عدّل مديرٌ (نشط في الشركة 2) اسمَ ذلك المستخدم فقط → تنهار إسناداته إلى [2] بصمت. حتى للسوبر أدمن: أي تحديث لا يرسل القائمة الكاملة يمسحها ويجعل `CompanyId = null`.
**الإصلاح:**
- لغير السوبر أدمن: **لا تلمس `AssignedCompanies` إطلاقاً** إن لم يكن مخوّلاً بإدارتها؛ عدّل الحقول الأخرى فقط.
- للسوبر أدمن: عدّل الإسنادات فقط عند إرسال `CompanyIds != null` (تمييز «لم يُرسل» عن «قائمة فارغة»)، وامنع إفراغ شركات دور غير‑سوبر‑أدمن.
- تحقّق: يجب أن يملك المستخدم غير السوبر أدمن **شركة واحدة على الأقل** (حارس تحقّق).

### 🟠 B6 — ملفات يتيمة بعد الحذف
**الموقع:** `CompaniesController.cs:137‑151` — يحذف سجلات الأرشيف/القوالب/الكتب لكن يحذف **شعار الشركة فقط** من التخزين. تبقى: مرفقات الأرشيف (`Attachment.BlobKey`)، صور القوالب (هيدر/فوتر/علامة مائية)، ملفات PDF المولّدة (`GeneratedPdfBlobKey`).
**الإصلاح:** يسقط عملياً إن اعتمدنا التعطيل (B2). وإن أُبقي الحذف، اجمع كل مفاتيح الـ Blob واحذفها ضمن نفس العملية.

### 🟡 B7 — قِدَم قائمة الشركات في التوكن
**الموقع:** `JwtTokenService.cs:46` (claim `cids` يُبنى لحظة الدخول) + `api_client.dart` (لا Interceptor لتجديد التوكن).
**الأثر:** عمر التوكن 60 دقيقة (`JwtSettings.cs:10`)، وبلا تجديد تلقائي، تغييرات إسناد الشركات لا تظهر حتى إعادة الدخول. مقبول أمنياً لكنه مربك للمستخدم.
**الإصلاح:** Interceptor في Dio يجدّد عبر Refresh Token عند 401 (مقترح مسبقاً في status-report)، مع تحديث `AllowedCompanyIds` من `/auth/me` أو من نتيجة التجديد.

### 🟡 B8 — CORS مفتوح في الإنتاج
**الموقع:** `Program.cs:68‑76` — `AllowedOrigins` غير موجود في `appsettings.json` → القائمة فارغة → **fallback إلى `AllowAnyOrigin()`** حتى في الإنتاج.
**الإصلاح:** أضِف `AllowedOrigins` صراحةً لإعداد الإنتاج، وفي غيابه **ارفض** بدل السماح للكل (fail‑closed).

### 🟡 B9 — لا فشل سريع على الأسرار الناقصة
**الموقع:** `Program.cs:39‑57` + `appsettings.json` (SigningKey/QR فارغة).
**الإصلاح:** تحقّق عند الإقلاع: إن كانت البيئة إنتاجاً و`SigningKey` (أو مفاتيح QR) فارغة → أوقِف التشغيل برسالة واضحة بدل أعطال لاحقة غامضة عند إصدار التوكن/التوقيع.

### 🟡 B10 — `GET /companies/{id}` غير متسق مع القائمة
**الموقع:** `CompaniesController.cs:35‑38` — لغير السوبر أدمن يعتمد على الـ Query Filter (الشركة النشطة فقط)، بينما `List` تُظهر كل `AllowedCompanyIds`. فرئيس شركة على شركتين قد يفشل في فتح تفاصيل الشركة غير النشطة.
**الإصلاح:** وحّد المنطق: استخدم `AllowedCompanyIds` هنا أيضاً (كما في `List`/`Update`).

### 🟢 B11 — Migration فارغة وغير مُودَعة

### 🟢 B12 — حيلة الشركة `-1`

### 🟢 B13 — ترتيب الكتابة في التعديل بعد الاعتماد

**الإصلاح:** احفظ الـ Blob بمفتاح جديد ثم بدّل المرجع بعد نجاح الحفظ، أو غلّف بمعاملة/استراتيجية بحيث لا يُنشر الـ PDF إلا بعد ثبات الـ DB.

### ✅ المرحلة أ — إيقاف النزيف الأمني (مُنفَّذة ومُتحقَّق منها — 2026-07-14)

## 5) القرارات المعتمدة (محسومة مع المالك — 2026-07-13)

- **D1 — حذف الشركة: حلّ هجين ✅.** زر **تعطيل** (`IsActive=false`) + زر **حذف جذري** مع **تحقّق مسبق**: يُمنع الحذف فقط إن وُجد كتاب صادر **معتمد (Final)** — **المسودات تُتجاهل** (تُحذف مع الشركة). *(نقطة قيد التأكيد: هل يمنع وجود سجلات أرشيف الحذف أيضاً؟ التوصية: نعم لأن الأرشيف سجل رسمي بلا مفهوم «مسودة».)* بيانات الإعداد (قوالب/جهات/أنواع/أسعار صرف/روابط مستخدمين/مسودات) تُنظَّف تلقائياً. الحذف يُغلَّف بـ `ExecutionStrategy` وينظّف كل ملفات التخزين (شعار/صور قوالب/مرفقات/PDF مولّدة).
- **D2 — النموذج: شركة رئيسية + شركات مُسندة ✅.** يبقى `User.CompanyId` (رئيسية) مع `AssignedCompanies`. ربط المستخدم بشركة/عدة شركات = **صلاحية حصرية للسوبر أدمن ورئيس الشركة** (المدير/الموظف لا يربطان). رئيس الشركة مقيّد بشركاته وبمن هم أدنى منه.
- **D3 — النظام يبدأ فارغاً ✅** مع تحسين تجربة أول تشغيل (إزالة حيلة `-1` واستبدالها بحالة صريحة توجّه لإنشاء أول شركة).
- **D4 — الأقسام (ميزة جديدة) ✅ — الحسم النهائي:** الأقسام الستة الرسمية = **الصادر · الأرشيف · التقارير · المستخدمون · الإعدادات · النسخ الاحتياطي**. مستوى الدقة = **«وصول / لا وصول» للقسم فقط** (بلا تمييز عرض/تعديل). السوبر أدمن/رئيس الشركة يمنحان الربط بالشركات ويقيّدان المدير/الموظف على هذه الأقسام. **ميزة مستقلة تُصمَّم وتُنفَّذ بعد المرحلة (أ)** (ADR-012). راجع §4.
- **D4-قيد — رئيس الشركة ✅:** يمنح الصلاحيات ويربط المدير/الموظف بشركاته المسموحة له فقط ومن هم أدنى منه، **ويستطيع إنشاء شركة جديدة متى شاء**. *(تنبيه: هذا توسيع لـ ADR-009 الذي كان يقصر إنشاء الشركات على السوبر أدمن — سيُحدَّث ADR-009 وفق هذا القرار.)*
- **D5 — نبدأ بالمرحلة (أ) فقط ✅** (الأمان العاجل)، ثم مراجعة قبل المتابعة.

> **تبعات القرارات على الخطة:**
> - B5 (تحديث المستخدم يمحو الإسنادات) يُنقل للدفعة التالية لارتباطه بـ D4 ومنطق «من يعدّل الإسناد» — إلا إن طُلب إدراج حدّه الأدنى (منع غير سوبر‑أدمن/رئيس من مسح الإسنادات) ضمن (أ).
> - ميزة الأقسام (D4) تتطلب: كيان/حقل صلاحيات أقسام على المستخدم، فرضها في الباك-إند (Controllers/Services للصادر/الأرشيف/التقارير)، وإخفاء عناصر التنقّل بالواجهة. ADR جديد يوثّقها.
