## 1) الملخص التنفيذي

### القرار
نشر النظام على **جهاز واحد داخل مكتب الشركة (Mini PC)**، والوصول إليه من الخارج عبر
**Cloudflare Tunnel** بلا فتح أي منفذ في جدار الحماية، مع نسخ احتياطي ثلاثي الطبقات
(محلي + قرص خارجي + OneDrive).

### لماذا
| المطلب | كيف يتحقق |
|---|---|
| البيانات لا تغادر الشركة | لا سحابة — الأصل داخل المكتب |
| بلا تكلفة شهرية | شراء لمرة واحدة + دومين سنوي زهيد |
| الوصول من خارج العراق (٢–٣ موظفين) | Cloudflare Tunnel |
| أمان الشبكة | **صفر منافذ مفتوحة** — أأمن من فتح المنافذ |
| نجاة من حريق/سرقة | نسخة خارج المبنى على OneDrive |

### الأثر على الكود
> **صفر تعديل على منطق العمل.** الكود الحالي يعمل كما هو.
> الأعمال البرمجية المطلوبة (المرحلة أ) كلها **إضافات تشغيلية**: استعادة النسخة الاحتياطية،
> سياسة الاحتفاظ، تشغيل الـ API كخدمة ويندوز، وتأمين الأسرار.

### الحقائق التي حسمت القرار
| # | الحقيقة | لماذا تحسم |
|---|---|---|
| 1 | الترقيم يستخدم قفلاً صفّياً (`UPDLOCK`) في [`NumberingService.cs`](../../backend/Dms.Infrastructure/Services/NumberingService.cs) | يتطلب **قاعدة بيانات واحدة**؛ توزيعها ⇒ أرقام مكرّرة لكتب رسمية |
| 2 | كل الصلاحيات مفروضة في الباك-إند | قاعدة على جهاز المستخدم ⇒ يفتحها ويرقّي نفسه لسوبر أدمن |
| 3 | مفتاح توقيع QR يعيش في إعدادات الخادم | توزيعه ⇒ أي موظف يُزوّر كتاباً بتوقيع صحيح |
| 4 | التقرير المالي والبحث يجمعان من كل الوحدات | بيانات موزّعة ⇒ لا تقرير ولا بحث شامل |

## 2) لماذا هذا الخيار — التحليل الكامل

### البدائل المدروسة ولماذا استُبعدت

#### ❌ بلا سيرفر (كل شيء على جهاز الموظف)
**غير ممكن تقنياً** للأسباب الأربعة في الجدول أعلاه. تفصيلها:

- **الترقيم:** موظفان ينشئان كتاباً في نفس اللحظة على قاعدتين منفصلتين ⇒ كلاهما يحصل على
  `DEN-2026-00042`. كتابان رسميان بنفس الرقم يذهبان لجهتين مختلفتين، ولا يُكتشف إلا متأخراً.
  لا حل بدون نقطة مركزية تمنح الأرقام.
- **الصلاحيات:** من يملك ملف قاعدة البيانات يملك القرار — يفتحه بأي أداة SQL مجانية
  ويغيّر دوره، أو يعدّل كتاباً معتمداً، أو يمسح سجل التدقيق الذي يوثّق فعلته.
- **التوقيع:** مفتاح ECDSA الخاص هو ما يجعل الكتب غير قابلة للتزوير (وهو سبب وجود Phase 0).
  توزيعه على الأجهزة = استخراجه = تزوير بتوقيع يجتاز التحقق.
- **العمليات:** كيف يصل الكتاب من الموظف لمديره للاعتماد؟ يتطلب بناء نظام مزامنة وحلّ
  تعارضات — أصعب بكثير من سيرفر. والتقرير المالي لن يكتمل إلا إذا كانت كل الأجهزة تعمل.
  ودخول الرئيس على كل جهاز يتطلب فتح منفذ على **كل جهاز** — أي ٨ أهداف للاختراق بدل واحد.

#### ❌ Firebase
قاعدة **NoSQL**. النظام مبني على علاقات ومعاملات وأقفال صفّية وفلاتر عامة.
الانتقال = **إعادة كتابة الباك-إند من الصفر** (~6,400 سطر) + فقدان الأقفال الصفّية
التي يعتمد عليها الترقيم. خسارة شهور مقابل نظام أضعف.

#### ⚠️ Supabase
قاعدته PostgreSQL (علائقية حقيقية) فهو أقرب من Firebase، **لكن**:
- **لا يشغّل .NET** ⇒ تحتاج Supabase للقاعدة **+ مزوّداً آخر للـ API** = حسابان وفاتورتان.
- ثلاثة مواضع في الكود مرتبطة بـ SQL Server تحديداً وتحتاج إعادة كتابة:

| الموضع | التغيير المطلوب |
|---|---|
| [`NumberingService.cs:22`](../../backend/Dms.Infrastructure/Services/NumberingService.cs) | `WITH (UPDLOCK, HOLDLOCK)` ⇐ صيغة SQL Server ⇒ `SELECT … FOR UPDATE` |
| [`BackupService.cs:48`](../../backend/Dms.Infrastructure/Backup/BackupService.cs) | `BACKUP DATABASE` غير موجود في Postgres ⇒ إعادة كتابة بـ `pg_dump` |
| Migrations (23 ملفاً) | إعادة توليدها بالكامل |

**المحصلة:** أيام عمل للانتقال من قاعدة تعمل إلى قاعدة تعمل — خارج الشركة وبتكلفة شهرية.
لا مبرّر.

#### ⚠️ DigitalOcean / Azure
يعملان بلا مشاكل تقنية، لكن: تكلفة شهرية متكرّرة + البيانات خارج الشركة.
مناسبان لو كانت الشركة بلا مقر ثابت أو بلا من يصون جهازاً — وليست حالتنا.

#### ℹ️ توضيح عن Cloudflare
**Cloudflare لا يستضيف تطبيقات .NET.** دوره هنا:
الدومين · DNS · شهادة HTTPS مجانية · حماية من هجمات الحرمان · **و Cloudflare Tunnel**
وهو الجزء الأثمن (انظر المرحلة ج).

## 3) المعمارية النهائية

```
                     ┌──────────────────────────────────┐
                     │      Cloudflare (مجاني)          │
   الموظفون خارج     │  dms.<domain>  ·  HTTPS  ·  DDoS  │
   العراق (٢–٣)  ───▶│                                  │
                     └───────────────┬──────────────────┘
                                     │  نفق صادر مشفّر
                                     │  (بلا منافذ مفتوحة)
   ┌─────────────────────────────────▼──────────────────────────────┐
   │                  مكتب الشركة                                    │
   │                                                                 │
   │   موظفو المكتب ──(واي-فاي)──▶ الراوتر ──(كيبل)──▶ Mini PC       │
   │   (٥–٦ أجهزة)                                    ┌────────────┐ │
   │                                                  │ Dms.Api    │ │
   │                                                  │ (خدمة)     │ │
   │                                                  │ SQL Express│ │
   │                                                  │ الملفات     │ │
   │                                                  │ cloudflared│ │
   │                                                  └─────┬──────┘ │
   │                                                        │        │
   │                              قرص خارجي ◀───────────────┤        │
   │                              (يدوي دوري)               │        │
   └────────────────────────────────────────────────────────┼────────┘
                                                            │
                                              OneDrive ◀────┘
                                          (رفع تلقائي — خارج المبنى)
```

### طبقات التخزين — أيّها الأصل؟

> **النسخ ليست متساوية.** هناك أصل واحد وبقيتها مشتقّة.

| الطبقة | المحتوى | من يملكها | لو ضاعت |
|---|---|---|---|
| 🏛️ **Mini PC** | **الأصل الرسمي** — قاعدة البيانات + كل الملفات | النظام | كارثة — مصدر الحقيقة |
| 💻 **جهاز المستخدم** | نسخة PDF للاطلاع | المستخدم | **لا شيء** — مجرد راحة |
| 💾 **قرص خارجي** | نسخة احتياطية | المالك | تبقى OneDrive |
| ☁️ **OneDrive** | نسخة خارج المبنى | المالك | يبقى القرص |

**الملف على جهاز الموظف نسخة اطلاع لا سجل رسمي.** لو حُذف أو عُدّل لا يتأثر النظام —
الأصل في السيرفر بختمه ورقمه وتوقيعه. هذا يمنع سؤال «أي نسخة هي الصحيحة؟» مستقبلاً:
**الجواب دائماً التي في السيرفر.**

### الحسابات — فصل تام

| النظام | الحسابات | من يملك |
|---|---|---|
| **DMS** | **لكل موظف حساب خاص** (مبني بالفعل) | كل موظف |
| **OneDrive** | **حساب واحد** على السيرفر فقط | المالك وحده |
| **Windows على السيرفر** | حساب المالك فقط | المالك |

> 🔒 **لا موظف يدخل على OneDrive إطلاقاً — ولا يعرف بوجوده.**
> لو كان لهم وصول لاستطاع أي منهم حذف النسخ الاحتياطية أو العبث بها،
> أي أن نبني حماية ثم نعطي مفتاحها للجميع.

> 🔒 **النسخ الاحتياطي محصور بالسوبر أدمن داخل البرنامج** — مفروض بالفعل في
> [`BackupController.cs:11`](../../backend/Dms.Api/Controllers/BackupController.cs).
> لا الموظف ولا المدير ولا رئيس الشركة يأخذ نسخة أو ينزّلها.

> ⚠️ **فصل مهم:** OneDrive للنسخ الاحتياطي = اشتراك **واحد** على السيرفر.
> Office للموظفين = ترخيص لكل موظف، **قرار إداري منفصل تماماً** لا علاقة له بـ DMS.

### الوصول من داخل المكتب
**الجميع يستخدم نفس الرابط** (`dms.<domain>`) داخل المكتب وخارجه.

| | الطريق الخارجي (المعتمد) | الطريق المحلي (بديل مؤجَّل) |
|---|---|---|
| المسار | الجهاز ← الراوتر ← الإنترنت ← Cloudflare ← السيرفر | الجهاز ← الراوتر ← السيرفر |
| HTTPS | ✅ تلقائي | ❌ يحتاج شهادة محلية |
| الإعداد | **صفر** | ضبط DNS في الراوتر |
| لو انقطع النت | يتوقف الجميع | يعمل الداخليون |

**المعتمد: الطريق الخارجي للجميع** — عنوان واحد، تعليمات واحدة، دعم تافه، وتجربة متطابقة
للجميع (وبما أن ٢–٣ خارج العراق سيمرّون عبر النفق حتماً، فالتوحيد أبسط).
التأخير أجزاء من الثانية وغير محسوس في نظام وثائق.

**العيب المقبول:** لو انقطع نت المكتب يتوقف الجميع حتى الجالس بجانب السيرفر.
مخفَّف بـ: النت مستقر · **وضع دون اتصال مبني أصلاً** ويغطي إنشاء المسودّات.
إن أزعج لاحقاً، يُضاف الطريق المحلي (DNS محلي في الراوتر + شهادة).

- **الواي-فاي يكفي للموظفين** — لا حاجة لتسليك كيبلات.
- **⚠️ الـ Mini PC بكيبل إلزاماً** (لا واي-فاي): السيرفر يحتاج اتصالاً ثابتاً، والنفق يجب أن
  يبقى حياً، ورفع النسخ أسرع وأثبت. كيبل واحد من الراوتر المجاور.
- **⚠️ عنوان IP محلي ثابت** للـ Mini PC (أو حجز DHCP في الراوتر) وإلا انكسرت الإعدادات
  عند إعادة تشغيل الراوتر.

## 4) المكوّنات والتكاليف

### الجهاز — مواصفات مقترحة لـ ٨ مستخدمين

> 🎁 **النظام لا يخزّن الملفات في قاعدة البيانات** — القاعدة تحفظ البيانات والمفاتيح فقط
> (الملفات على القرص عبر `IFileStorage`). لذلك **SQL Server Express المجاني يكفي**:
> حدّه ١٠ جيجا للقاعدة، وقاعدتك نصوص وأرقام ⇒ تكفي لمئات آلاف الكتب.
> **صفر تكلفة ترخيص قاعدة بيانات.**

| المكوّن | التوصية | لماذا |
|---|---|---|
| المعالج | Intel N100/N150 أو Ryzen 5 | ٨ مستخدمين حِمل خفيف؛ N100 ~6 واط مناسب للعمل ٢٤/٧ |
| الذاكرة | **16 جيجا** | SQL Server يحب الذاكرة؛ ٨ تعمل و١٦ ترتاح |
| التخزين | NVMe 512 ج.ب (نظام + قاعدة) **+** قرص ثانٍ 1 ت.ب (ملفات + نسخ) | فصل القرصين: تلف أحدهما لا يأخذ الآخر |
| النظام | **Windows 11 Pro** | يلزم لسطح المكتب البعيد و BitLocker |
| ⚡ **UPS** | **إلزامي** | انقطاع كهرباء أثناء كتابة في القاعدة **قد يُتلفها**. جهاز يحمل وثائق رسمية لا يُترك بلا UPS |
| قرص خارجي | 1 ت.ب أو أكثر | نسخة الطبقة الثانية |

### التكاليف

| البند | النوع | ملاحظة |
|---|---|---|
| Mini PC + UPS + قرص خارجي | **شراء لمرة واحدة** | التكلفة الأساسية |
| Windows 11 Pro | لمرة واحدة | غالباً مضمّن مع الجهاز |
| SQL Server Express | **مجاني** | كافٍ تماماً |
| Cloudflare (Tunnel + DNS + HTTPS) | **مجاني** | الخطة المجانية تكفي |
| الدومين | **سنوي زهيد** | انظر المرحلة ج |
| Microsoft 365 (OneDrive) | **سنوي** | انظر المرحلة د |
| **الاستضافة الشهرية** | **صفر** | ✅ الهدف المحقّق |

> ⚠️ **الأسعار تتغيّر** — تحقّق من الأسعار الحالية عند الشراء. هذا الملف لا يذكر أرقاماً
> لأنها تتقادم أسرع من بقية المحتوى.

## 5) المرحلة أ — الأعمال البرمجية (قبل الشراء)

> هذه المهام **لا تحتاج الجهاز** — أنفّذها بينما تشتري.

### أ-1 — سياسة الاحتفاظ بالنسخ 🔴 حرجة

**المشكلة المكتشفة:** فحص [`BackupService.cs`](../../backend/Dms.Infrastructure/Backup/BackupService.cs) كشف أمرين:
1. **كل نسخة كاملة** — تضغط القاعدة **+ كل ملفات التخزين** من جديد في كل مرة.
2. **لا سياسة حذف** — النسخ القديمة تتراكم للأبد.

يعمل الآن (٢٥ ميجا) لأن البيانات قليلة. مع الاستخدام الحقيقي:

**الحساب** (بافتراض ٤٠ وارداً ممسوحاً + ٣٠ صادراً شهرياً):

| | الحجم |
|---|---|
| نمو الملفات | ~1 ج.ب سنوياً |
| بعد ٣ سنوات | ~3 ج.ب |
| النسخة الواحدة | ~2.5 ج.ب |
| **يومية بلا حذف — سنة** | **~365 ج.ب** ❌ |

**أي حزمة تخزين ستمتلئ خلال أشهر** — ليس لأن البيانات كبيرة بل لأننا نكرّر نفس الملفات ٣٦٥ مرة.

**الحل — تعديلان:**

**1. سياسة احتفاظ (جد/أب/ابن):** ٧ يومية + ٤ أسبوعية + ١٢ شهرية = **٢٣ نسخة بدل ٣٦٥**

| | بلا سياسة | مع السياسة |
|---|---|---|
| الاستهلاك بعد سنة | ~365 ج.ب | **~58 ج.ب** ✅ |

**2. فصل القاعدة عن الملفات:** الوثائق **لا تتغيّر بعد إنشائها** ⇒ لا معنى لنسخها يومياً.
- **يومياً:** قاعدة البيانات فقط (عشرات الميجا)
- **أسبوعياً/شهرياً:** نسخة كاملة بالملفات

⇒ الرفع اليومي سريع وخفيف.

### أ-2 — استعادة النسخة الاحتياطية 🔴 حرجة (الفجوة G1)
معيار قبول v1 ينصّ «تُنشأ **وتُستعاد**». حالياً الاستعادة يدوية على السيرفر.
**تزداد أهمية مع السيرفر الداخلي** — لا مزوّد سحابي يتدخّل نيابةً عنك.

النطاق: نقطة استعادة (سوبر أدمن فقط) + تحققات سلامة قبل الاستبدال + وضع صيانة أثناء
العملية + سجل تدقيق. **بتأكيد صريح مضاعف** — عملية تدميرية بطبيعتها.

### أ-3 — تشغيل الـ API كخدمة ويندوز 🟠
حالياً `dotnet run` في نافذة: تُغلق النافذة ⇒ يتوقف النظام؛ يُعاد تشغيل الجهاز ⇒ لا يعود.
**على السيرفر يجب أن يبدأ تلقائياً مع الإقلاع ويُعيد تشغيل نفسه عند أي تعطّل.**

### أ-4 — تأمين الأسرار بلا Key Vault 🟠
الخطة قالت Azure Key Vault. بلا Azure، البديل المعتمد:
**BitLocker على القرص + صلاحيات NTFS مشدّدة على ملف الإعدادات** (حساب الخدمة فقط).
مجاني ومناسب لسيرفر داخلي مادياً تحت سيطرتك.

### أ-5 — نسخة محلية على جهاز المستخدم 🟡
بعد اعتماد الكتاب، ينزل الـ PDF تلقائياً لمجلد على جهاز المستخدم.
**ميزة صغيرة لا تغيير معماري** — الأصل يبقى في السيرفر.

### أ-6 — سكربت التحديث 🟡
بدل خطوات يدوية تُنسى: إيقاف الخدمة ← نسخة احتياطية ← استبدال الملفات ← `migrations` ← تشغيل ← تحقق.

## 7) المرحلة ج — الدومين و Cloudflare من الصفر

### ج-1 — اختيار اسم الدومين

**معايير الاختيار:**
- قصير وسهل الإملاء (سيُكتب يدوياً أحياناً)
- يعكس اسم الشركة (DEN LAND / أرض العرين)
- **مفضّل `.com`** — الأسهل شراءً والأرخص والأوسع دعماً

**⚠️ فرق مهم بين الامتدادات:**

| | `.com` (مُوصى به) | `.iq` |
|---|---|---|
| الشراء | من Cloudflare مباشرة | **مسجّل عراقي محلي فقط** |
| المتطلبات | لا شيء | غالباً وثائق تثبت كيان عراقي |
| السعر | زهيد وقياسي | أعلى ومتغيّر |
| الربط بـ Cloudflare | **تلقائي** | يدوي — تغيير خوادم الأسماء |
| التجديد | تلقائي | متابعة يدوية |

> **التوصية: `.com` عبر Cloudflare** — لأنك ستستخدم Cloudflare أصلاً، فالشراء منهم يجعل
> الدومين مربوطاً **تلقائياً** بلا خطوات إضافية. Cloudflare يبيع بسعر التكلفة بلا هوامش.

**العنوان النهائي سيكون:** `dms.<اسمك>.com`
(نستخدم نطاقاً فرعياً `dms` لتبقى `<اسمك>.com` متاحة لموقع الشركة مستقبلاً.)

### ج-2 — شراء الدومين (خطوة بخطوة)

1. افتح `dash.cloudflare.com` وأنشئ حساباً (بريد + كلمة مرور).
2. **فعّل المصادقة الثنائية فوراً** — هذا الحساب يتحكم بعنوان نظامك كله.
3. من القائمة: **Domain Registration** ← **Register Domain**.
4. ابحث عن الاسم؛ إن كان متاحاً أضفه للسلة.
5. أكمل الدفع (بطاقة دولية). ⚠️ **فعّل التجديد التلقائي** — دومين منتهٍ = نظام متوقف.
6. بعد الشراء يظهر الدومين في حسابك **مربوطاً تلقائياً** بـ DNS الخاص بهم.

> **لو اشتريت من مسجّل آخر:** بعد الشراء، غيّر **خوادم الأسماء (Nameservers)** لتلك التي
> يعطيك إياها Cloudflare، وانتظر حتى ٢٤ ساعة للانتشار.

### ج-3 — ما هو Cloudflare Tunnel ولماذا؟

**المشكلة التقليدية:** للوصول لسيرفر داخلي من الخارج، تفتح منفذاً في راوتر الشركة
(Port Forwarding). النتيجة: سيرفرك **مكشوف للإنترنت كله**، وأي ثغرة تصبح باباً مفتوحاً،
وستُهاجَم آلياً خلال ساعات.

**الحل:** برنامج صغير (`cloudflared`) على السيرفر **يفتح هو اتصالاً للخارج** نحو Cloudflare
(كما يفعل أي متصفح)، ويبقى الاتصال مفتوحاً. الزوّار يصلون Cloudflare، وهو يمرّر الطلبات
عبر النفق القائم.

| | فتح المنافذ | Cloudflare Tunnel |
|---|---|---|
| منافذ مفتوحة | ✅ نعم — خطر | ❌ **صفر** |
| IP السيرفر ظاهر | نعم | لا — مخفي |
| شهادة HTTPS | تشتريها وتجدّدها | **مجانية وتلقائية** |
| حماية DDoS | لا | ✅ مضمّنة |
| يعمل مع IP متغيّر | لا | ✅ نعم |

### ج-4 — إعداد النفق

1. على الـ Mini PC: نزّل `cloudflared` لويندوز من الموقع الرسمي.
2. `cloudflared tunnel login` ← يفتح المتصفح لتسجّل الدخول وتأذن.
3. `cloudflared tunnel create dms` ← يُنشئ النفق ويحفظ ملف اعتماد. **احتفظ بنسخة منه.**
4. أنشئ ملف إعدادات يربط `dms.<domain>` بـ `http://localhost:5080`.
5. `cloudflared tunnel route dns dms dms.<domain>` ← يُنشئ سجل DNS تلقائياً.
6. **ثبّته كخدمة ويندوز** ليعمل تلقائياً مع الإقلاع (`cloudflared service install`).
7. اختبر من هاتف على **بيانات الجوال** (لا واي-فاي المكتب) — أهم اختبار.

> ⚠️ الأوامر الدقيقة قد تتغيّر مع إصدارات `cloudflared`. **الوثائق الرسمية هي المرجع.**

### ج-5 — تشديد الأمان بعد التشغيل

| الإعداد | الغرض |
|---|---|
| **Always Use HTTPS** | تحويل أي طلب HTTP تلقائياً |
| **Minimum TLS 1.2** | رفض البروتوكولات القديمة |
| قواعد جدار حماية (اختياري) | حصر الوصول بدول محددة — أنت تعرف من أين يعمل موظفوك |
| Cloudflare Access (اختياري) | طبقة مصادقة **قبل** الوصول للتطبيق أصلاً |
| ⚠️ **مصادقة ثنائية على حساب Cloudflare** | **إلزامي** — يتحكم بعنوانك كله |

## 8) المرحلة د — النسخ الاحتياطي ٣-٢-١

> **٣** نسخ · على **٢** وسيطين · و**١** خارج المبنى.
> السيرفر الداخلي بلا نسخة خارج المبنى = حريق واحد يمحو تاريخ الشركة.

| الطبقة | الوسيط | التكرار | يحمي من |
|---|---|---|---|
| 1 | قرص السيرفر | يومي (مجدول) | حذف بالخطأ، خطأ بشري |
| 2 | قرص خارجي | دوري يدوي (أنت) | تلف السيرفر أو أقراصه |
| 3 | **OneDrive** | تلقائي مع كل نسخة | **حريق · سرقة · عبث** |

### د-1 — اختيار خدمة السحابة

| | **OneDrive (Microsoft 365)** ⭐ | Google Drive | Cloudflare R2 / Backblaze |
|---|---|---|---|
| العمل المطلوب | **صفر** (برنامج مزامنة) | صفر | يحتاج برمجة |
| استرجاع بعد فدية/عبث | ✅ **استرجاع كامل حتى ٣٠ يوماً** | سلة محذوفات ٣٠ يوماً | ✅ قفل كائنات (الأقوى) |
| يشمل Office | ✅ | ❌ | ❌ |
| مناسب الآن | ⭐ **الأنسب** | جيد | لاحقاً |

**التوصية: Microsoft 365 (OneDrive)** لسببين:
1. **الاسترجاع الزمني** — لو أصاب الجهاز فيروس فدية أو عبث أحدهم، تُرجع OneDrive كله
   لنقطة زمنية سابقة. هذه بالضبط الحماية المطلوبة.
2. سعة أكبر بسعر قريب + تطبيقات Office.

> ⚠️ **المزامنة ليست نسخاً احتياطياً:** لو حُذف ملف على الجهاز، **المزامنة تحذفه من
> السحابة أيضاً**. لهذا ميزة الاسترجاع الزمني ليست رفاهية — هي **ما يحوّل المزامنة
> إلى نسخ احتياطي حقيقي**. تأكّد من تفعيلها وفهم كيفية استخدامها **قبل** أن تحتاجها.

### د-2 — الإعداد
1. اشتراك Microsoft 365 + تثبيت OneDrive على الـ Mini PC بحساب **يخصّك وحدك**.
2. توجيه مجلد النسخ الاحتياطي ليكون داخل مجلد OneDrive ⇒ رفع تلقائي.
3. **إيقاف "Files On-Demand"** لمجلد النسخ — نريد نسخة حقيقية محلياً وسحابياً معاً.
4. التحقق من تفعيل سجل الإصدارات والاسترجاع الزمني.
5. **تنبيه امتلاء السعة** — نسخة لا تُرفع بصمت لأن السعة امتلأت = نسخة غير موجودة.

### د-3 — السعة المطلوبة
مع سياسة الاحتفاظ (أ-1): **~58 ج.ب بعد سنة**، ينمو تدريجياً.
**٢٠٠ ج.ب تكفي سنوات** — لكن **فقط مع سياسة الاحتفاظ**؛ بدونها لا تكفي أي حزمة.

## ملحق: الفروق عن الخطة الأصلية

| الموضوع | خطة العمل v2.2 | هذه الخطة | السبب |
|---|---|---|---|
| الاستضافة | Azure App Service | **سيرفر داخلي** | تكلفة صفرية + البيانات داخل الشركة |
| التخزين | Azure Blob | **قرص محلي** (`IFileStorage` يدعم الاثنين) | لا سحابة |
| الأسرار | Azure Key Vault | **BitLocker + NTFS** | لا Azure؛ الجهاز تحت سيطرة مادية |
| قاعدة البيانات | Azure SQL | **SQL Express** (مجاني) | القاعدة صغيرة (لا تحوي ملفات) |
| الوصول الخارجي | عنوان عام | **Cloudflare Tunnel** | أأمن — صفر منافذ مفتوحة |
| النسخ الاحتياطي | Azure تلقائي | **٣-٢-١ يدوي/مجدول** | مسؤوليتنا الآن — لذا الاستعادة حرجة |

> التجريد `IFileStorage` المصمَّم في Phase 0 يجعل العودة لـ Azure Blob مستقبلاً **تغيير
> إعداد لا إعادة كتابة** — القرار قابل للعكس إن كبرت الشركة.
